# CAR / Agenda / Packet Module — Build Spec

**Part of:** Franklin Service Request System (OneFranklin) — in-house replacement for the CivicPlus Minutes & Agendas module.
**Scope:** Council Action Report (CAR) submission and review, meeting cycle scheduling, work sessions, agenda generation, and packet assembly. Minutes are out of scope (handled separately via existing Copilot agent).
**Stack:** React/Vite/Supabase/Vercel — same stack and patterns as the rest of the app (MOU module, RSA 91-A workflow, agenda-item sponsor pattern).

---

## 1. Actors & Access

| Actor | Access |
|---|---|
| Admin (bdemers@franklinnh.gov, citymgr@franklinnh.gov) | Full access: create/edit meeting cycles, review CARs, schedule work sessions, sign off on answer reports, generate agendas/packets, look up or reset submitter PINs, manually override any calculated date, reassign CARs across cycles/stages. This is the ONLY admin-facing surface — no other accounts should have access. |
| Public / any submitter (staff, council, public — no login required) | Can submit a CAR via the public form. Receives a submission ID + PIN. Can return to look up status and (if applicable) edit their submission using ID + PIN. No visibility into other submitters' CARs, review notes, or admin-only fields. |

Two-admin-only access should be enforced at the auth layer, not just hidden in the UI — this module should not be reachable by department-level staff logins that exist elsewhere in the app.

## 2. Data Model

### 2.1 Meeting Cycle
One record per City Council meeting.

| Field | Notes |
|---|---|
| Meeting Date | The only date the admin enters directly. |
| Meeting Type | e.g., Regular Council Meeting (this module is scoped to the Council meeting cycle; if Planning Board or other bodies need this later, treat as a separate cycle type). |
| Review Date (calculated) | Default: Meeting Date − 17 (see open item in §7 re: aligning with the published 21-day public guidance). Admin-editable override. |
| Answers-Due default offset | Used per work session (see §2.2) — not a single cycle-level date, since a cycle can have multiple work sessions. |
| Packet Publish Date (calculated) | Default: Meeting Date − 5. Admin-editable override. |
| CAR Submission Window Close | Defaults to Review Date. Admin-editable override. |
| Status | Open for submissions / In Review / Active (post-review) / Packet Published / Closed |

Every calculated date stores **both** its default (formula-derived) value and an optional actual/override value. Downstream logic and displayed dates always prefer the override when present, but the default stays visible/recoverable so an override isn't a one-way door.

### 2.2 Work Session
Zero, one, or many per Meeting Cycle. Created only when needed (i.e., not auto-generated by the cycle formula).

| Field | Notes |
|---|---|
| Parent Meeting Cycle | Link |
| Work Session Date | Admin-entered when scheduling the session. |
| Answers Due Date (calculated) | Default: Work Session Date + 2. Admin-editable override. |
| CARs assigned to this session | List of CARs routed here at review (see §3 status ladder). |

Optional but recommended: a soft validation warning (not a hard block) if a work session's Answers Due Date leaves fewer than ~5 days before the cycle's Packet Publish Date — flags a cycle that's getting squeezed, without preventing the admin from scheduling it anyway.

### 2.3 CAR (Council Action Report)
| Field | Notes |
|---|---|
| Submission ID | Auto-generated, shown to submitter. |
| PIN | Auto-generated, shown to submitter once; admin can look up or reset. |
| Submitter type | Staff / Council / Public |
| From | Per published CAR template — department, board, committee, staff member, or requesting organization. |
| Subject | Short, clear title of the requested action. |
| History | Background/context — prior Council actions, dates, committee discussion, prior votes, legal requirements. |
| Recommendation | The action being recommended. |
| Suggested Motion | Exact motion language for Council to vote on. |
| Discussion | Supporting detail — operational, legal, financial, timeline, public benefit, risks/alternatives. |
| Alternatives | Other options available to Council besides the recommendation. |
| Attachments / Exhibits | File uploads — supporting docs, maps, financials, contracts, resolutions, staff reports. |
| Resolution Template (conditional) | Included only if the action requires a resolution (per published guidance). |
| Current Meeting Cycle | Link — which cycle this CAR currently belongs to. |
| Current Work Session | Link, if applicable. |
| Status | See §3. |
| Review Decision | Reject / Approve – Normal Business / Approve – Hot Button, plus reviewer note. |
| Cycle Reassignment History | Log of any cycle/stage moves — from cycle, to cycle, from stage, to stage, reason, date, by whom. |

## 3. CAR Status Ladder

```
Submitted
  → Under Review (batch, at cycle's Review Date)
      → Rejected [terminal]
      → Approved – Normal Business → Included in Packet
      → Approved – Hot Button → Pending Work Session Assignment
          → Scheduled for Work Session
              → Answer Due
                  → Answer Submitted (pending sign-off)
                      → Answer Signed Off → Included in Packet
                      → [sign-off missed by Packet Publish Date] → Pushed to Reassignment
→ Included in Packet
  → Packet Published
      → Decided at Meeting [terminal]
```

**Reassignment** (from "Pushed to Reassignment," or manually at admin discretion) is an explicit admin action, not automatic:
- Admin picks the **target meeting cycle** from scheduled future cycles (does not default to "next").
- Admin picks the **target status/stage** within that cycle (e.g., back at Under Review, straight into a specific Work Session, at Answer Due) rather than the system inferring it.
- This gets logged in Cycle Reassignment History.

## 4. Public Submission Flow

1. Submitter lands on a public CAR intake page. Before the form, present **educational/guidance content** drawn from the CAR Resource Page — what requires a CAR, examples of good "From"/"Subject" entries, and a short explanation that CAR submission is a form of civic engagement.
2. Form fields match §2.3's CAR fields, with inline prep-question-style guidance per field (mirroring the resource page's field-by-field examples — e.g., under Recommendation: "State the action being recommended to City Council," with the grant-amendment example as a model).
3. Conditionally show the Resolution Template section if the submitter indicates the request needs a resolution.
4. On submit: assign Submission ID + PIN, display both to the submitter (this is their only chance to see the PIN in plaintext — make sure it's clearly presented, e.g., "save this now").
5. Submitter can return via a "Check Your CAR Status" page using Submission ID + PIN, to view status and, if the CAR is still editable (not yet past review), make edits.

## 5. Admin Flow

- **Meeting Cycle management:** create a cycle by entering a Meeting Date; system calculates Review, Packet Publish, and CAR Submission Window Close; all editable.
- **Batch Review:** on/after the cycle's Review Date, admin sees all CARs submitted into that cycle's window and records a decision per CAR (Reject / Approve – Normal / Approve – Hot) with an optional note.
- **Work Session scheduling:** admin creates one or more Work Session records under a cycle as needed, and assigns Hot-Button CARs to a specific session.
- **Answer sign-off:** admin reviews submitted answer reports and signs off (or sends back) before Packet Publish.
- **PIN lookup/reset:** admin can search by Submission ID or submitter info to view or reset a PIN (e.g., if a submitter loses it).
- **Packet generation:** admin triggers packet generation for a cycle once Packet Publish Date is reached (or on demand) — see §6.
- **Reassignment:** admin manually reassigns a CAR's cycle and status per §3.

## 6. Document Generation

- **Meeting logistics as data, not text:** each Meeting Cycle (and Work Session) record holds date, time, location, and meeting link as structured fields. Agenda templates reference these fields directly rather than having them retyped — updating the meeting record updates every generated document.
- **Two agenda templates:** Council Meeting pattern and Work Session pattern, matching the existing distinction in how these are structured today.
- **Packet = agenda (page one) + approved CARs' documents/attachments, in order** — generated as a single output rather than built separately and manually combined. "Approved" here means CARs with status Included in Packet as of generation time.

## 7. Open Items / Decisions Not Yet Made

These are flagged intentionally rather than guessed at — resolve before or during build:

1. **17-day vs. 21-day submission window.** The cycle math (review = meeting − 17) is 4 days shorter than the published CAR Resource Page guidance ("at least 3 weeks / 21 days prior"). Decide whether to adjust the internal Review Date default to meeting − 21 (and re-check downstream buffers) or update the published public-facing guidance to match the 17-day internal model.
2. **Multiple work sessions and answer sign-off timing.** If a cycle has more than one work session close together, confirm there's enough runway between the latest session's Answers Due and the cycle's Packet Publish Date. The soft-warning threshold (§2.2) is a starting suggestion, not finalized.
3. **Reassignment and re-review.** When a CAR is reassigned to a new cycle at a stage other than Under Review, confirm no re-review by the mayor/city manager is required — currently spec'd as skipping straight back in.
4. **Notification touchpoints.** Not yet specified whether submitters get automatic status-change emails (reusing the pattern from other modules) or need to check back manually via ID + PIN.
